Claude Managed Agents
到底是什么？

一句话结论

它是 Anthropic 官方托管的「Agent 运行时」：你只写 Agent 的配置（模型、提示词、工具、技能）， 剩下的 Agent 循环、工具执行、沙箱、会话状态、流式事件、计费与预算……全部由 Anthropic 的服务器替你跑。

官方把它和 Messages API 摆在两个端点：Messages API 给你「直接提问」和完全的控制权； Managed Agents 给你「一个跑在托管基础设施上的、可配置的 agent harness（Agent 骨架）」， 专治长任务和异步干活。

三种做法，别再混淆

方式Agent 循环 / 工具执行谁负责适合
Messages API你自己写（自家后端）要精细控制、自定义循环
Claude Agent SDKSDK 给你，但跑在你机器上本地/自建，进程内集成
Managed AgentsAnthropic 全托管（含沙箱）长时运行、状态持久、少运维

→ 官方还提供了「从 Messages / Agent SDK 迁移」的文档，说明这是它主推的下一代形态。

四个核心概念

Agent
模型 + 系统提示词 + 工具 + MCP 服务器 + Skills。建一次，拿到 ID 反复复用，可版本化、可归档。
Environment
「在哪跑」：Anthropic 云沙箱（每次会话一个全新 Linux 容器），或你自己机器上的自托管沙箱。
Session
一次运行实例。有状态：会话暂停可续跑，文件系统、对话历史、产出都留在服务端。
Events
你和 Agent 之间的事件流：用户消息、工具结果、状态更新，走 SSE 实时推回来，历史可完整取回。

跑一次，只要五步

① 建 Agent➜ ② 建 Environment➜ ③ 开会话➜ ④ 发事件 / 收流➜ ⑤ 干预或中断

Agent 和 Environment 可以用 ant apply 从 YAML/Markdown 声明式定义，ID 记到 claude-lock.json； SDK 侧就是 client.beta.agents.create() .environments.create() .sessions.create()。 所有端点走 beta 头 managed-agents-2026-04-01。

它自带的能力（这部分才是重点）

① 内置工具集

默认全开：bashreadwriteeditglobgrepweb_fetchweb_search，外加 MCP 服务器 和自定义工具。 小细节：单个工具输出超过 10 万字符，会自动落盘成文件，模型只看到截断预览 + 路径。

② 权限策略

  • always_allow：直接执行（agent 工具集默认）
  • always_ask：暂停等你点同意（MCP 工具集默认）
  • auto：由服务端逐次判断——放行 / 拒绝 / 挂起问你

③ 让它自己「验收」：Outcome

你写一份 Markdown 评分表（rubric），Harness 会另起一个 grader（独立上下文，避免自我感觉良好）， 按条目打分并把意见回灌给 Agent，循环迭代直到达标。

④ 记忆与「做梦」

Memory store 会挂载进沙箱当普通目录，Agent 用文件工具读写。跑久了必然脏， 于是有了 Dreams（研究预览）：异步任务，读旧记忆库 + 最多 100 条历史会话，去重、纠错、提炼， 输出一个新的记忆库，旧的绝不被改写——不满意就丢掉。

⑤ 其他加分项

  • Vaults：集中保管 OAuth/API 凭证，支持轮换，会话里按需引用
  • Budgets：会话级预算上限，撞顶就暂停/可续，多 Agent 与定时任务也受控
  • Scheduled deployments：cron 定时跑，带时区语义与失败处理
  • 多 Agent 编排：subagents 分工、threads 并行、advisor 关键时刻给建议、dynamic workflows 动态编排
  • Webhooks / 事件增量 / 可观测性：不守着流也能接结果，能查每个会话的 token 与花费

云端沙箱 vs 自托管，怎么选

Cloud（默认）Self-hosted sandbox
工具/代码在哪跑Anthropic 托管容器你的 worker（你的机器）
什么上云全部对话历史、工具结果、skills、memory；文件与进程留在你这边
你要运维无worker 主机、加固、网络限制、环境密钥

还有更彻底的 Self-hosted Managed Agents：整套服务装进你自己的集群（Docker Compose 或 Helm chart cma-sandboxes）， 三把钥匙分工明确——Server API key（你的应用→你的服务器）、Inference credential（服务器→模型）、Environment key（worker→服务器）。 代价是服务器安全、记忆库托管、异常检测都归你；好处是唯一支持 ZDR 的形态。

谁该用？ 需要跑几分钟到几小时的 Agent 任务、要持久文件系统与会话历史、要 cron 定时跑、 不想自己写 agent loop 和沙箱、又或者有合规要求要把执行留在自己机房——这些都命中了。

⚠ 踩坑前先记住

  • Beta：所有端点必须带 managed-agents-2026-04-01，行为可能被调整。
  • 不适用 ZDR（托管版）：会话是有状态资源，转录会一直留着，直到你主动删会话；删文件要单独删。
  • 不支持 HIPAA BAA。MCP tunnels、Dreams 是更受限的研究预览，需单独申请。
  • 能上：Claude API、Claude Platform on AWS、Google Cloud 上的 Anthropic managed 版本。

我的三个判断

  1. 这是「Agent 的服务器端运行时」标准化。 以前每家自己造循环+沙箱，现在收敛成 Agent / Environment / Session / Event 四个原语——很像容器把「进程+隔离」标准化。
  2. 真正的护城河在「验收」和「记忆」。 Outcome+grader 把「做完了」变成可测的闭环；Dreams 解决长期记忆腐化——这两件事自己搭都很痛。
  3. 自托管是给合规开的门，不是给省钱开的。 它把 ZDR、数据驻留问题解决了，但把运维与安全责任全数退回给你。
