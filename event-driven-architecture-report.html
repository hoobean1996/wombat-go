Event-Driven 架构
到底是什么？

一句话结论

不再问「你帮我做件事」，而是宣告「这里发生了什么」，谁关心谁自己去接。发出的人 不知道、也不需要知道谁在听——这就是全部的秘密，也是全部的代价。

它不是一个框架，是一套耦合方式的选择：把「调用」换成「广播事实」， 换来解耦、削峰、可重放，付出的是看不见的控制流与最终一致。

先把三个词分开

消息说的是例子耦合
命令 Command「请把这件事做了」ReserveCredit指名叫人干，强
事件 Event「这件事已经发生了」（过去式）OrderCreated广播给世界，弱
查询 Query「现在是什么状态？」GetOrder同步，强

命名就是设计：事件永远用过去式，因为它记录的是既成事实，不可撤回、不可协商。

那"事件"到底是什么？

严格说，事件是状态的一次显著变化（车从"待售"变成"已售"）。发生的事本身不会旅行， 在网上飞的是它的通知消息。日常把通知也叫事件——行，但要知道这层偷换， 因为它解释了为什么事件总带着"消息中间件"的味道。

三种形态，别混为一谈（Fowler）

① 事件通知
事件很瘦，只说「订单 42 变了」，收的人自己回头来问详情。耦合最低、最好搭，但一旦业务流跨了好几个事件，它就变成一段"没写在任何代码里"的流程——难调试、难修改。
② 事件携带状态
事件里塞满数据，收的人本地存一份副本，从此不必再回来问。换来低延迟、抗故障（源系统挂了也能干活），代价是数据到处复制、带宽与一致性压力，以及接收端要处理乱序与重复。
③ 事件溯源
不存"当前状态"，只追加"变更日志"，状态由重放算出。能得到历史、能回放到任意时刻、能注入假设事件探索"另一种历史"（git 就是一本事件日志）。代价：版本演进、快照、重放成本、外部系统读不懂日志。
④ CQRS（顺带）
读写模型分开。它本身跟事件无关，只是常和上面三个一起用。Fowler 原话大意：很多同事对它很警惕，因为常被误用——一个项目说"事件溯源是灾难"，其实混淆了 CQRS。

→ 这四种组合方式不同，痛的地方完全不同。搞不清自己用的是哪种，就没法判断问题出在哪（Fowler 把这叫"植物学家难题"）。

两种拓扑：谁在管事

图 1 · 无中心广播 vs 中心编排（也可混着用）

Broker：性能与扩展性好，但出了事"没人负责"，排查靠观测。Mediator：把跨服务流程收进一处， 能重试、能补偿、能看进度，代价是多一跳、编排器自己别变成单点与瓶颈。

拆开一条事件看

{ header, payload } —— header：事件名、时间戳、类型、版本号、事件 id、关联/追踪 id、来源。 payload：变了什么。

胖事件（带全量数据）瘦事件（只带 id）
快、不用回查、源系统压力小
但多份数据副本、带宽贵、容易形成"印记耦合"		带宽省、耦合小、单一事实来源
但收的人要回查数据库，慢，源系统承压

→ 这是光谱不是二选一。真正要定的问题只有一个：收的人拿到这条消息后，还需不需要再问一句？

领域事件 vs 集成事件

领域事件：发生在一个限界上下文内部，payload 很瘦，因为听众多半就在同一个服务里，需求你清楚。 集成事件：跨上下文发布，是给外人看的契约，payload 更肥、更啰嗦——因为你不知道谁会听、拿它干什么， 宁可多说一点。

真正的驱动力：一致性与 2PC 的不可能

微服务拆库之后（Database per Service），一个业务事务横跨两个库，ACID 没了；分布式事务 2PC 基本不是选项。 于是：每个服务改了自己的数据，就发一条事件；别人订阅、更新自己的数据——用最终一致 换掉跨库事务。经典例子：订单服务发 OrderCreated（订单处于 pending）→ 客户服务试着占用额度， 回发 CreditReserved 或 CreditLimitExceeded → 订单服务据此把订单改成 approved 或 cancelled。

麻烦在于：可靠地同时做到「改库」和「发事件」，这件事本身就难，因为库和 broker 之间没有共同事务。四条常见解法：

  • 本地事务表（Transactional Outbox）：事件和业务数据写进同一个库、同一个事务，再由后台搬运出库。最常用
  • 事件溯源：日志即事实，写日志就是发布
  • 数据库触发器 / 事务日志捕获（CDC / log tailing）：从 binlog 里把变更捞出来发
  • Saga：一串本地事务 + 补偿动作，替掉长事务

上线前必须过的五道关

  • 至少一次投递 ⇒ 消费者必须幂等。重复是常态不是意外；幂等键（dedup key）与去重表是标配。
  • 顺序不保证。要么按 key 分区保序，要么让状态机容忍乱序（比较版本号/序号）。
  • 会丢吗？发事件与改库不是一个事务 → 这就是 outbox 存在的理由。别在进程里"先发后写"。
  • schema 演进。事件一旦发出去就是契约，删字段就等于毁约。版本化 + 只加不改 + 语义化版本， 消费者要能忽略不认识的字段。
  • 看不见的流程。事件驱动的流程不在任何源码里，只能在运行中看见——trace/correlation id 贯穿、 端到端可观测、再配一个"事件流视图"。这是 Fowler 点名的头号陷阱。

⚠ 反模式清单

  • 被动攻击式命令：心里想让人干活，却把消息写成事件的样子——发的人其实在等结果。该用命令就用命令。
  • 拿事件当 RPC：事件发出去、立刻同步等回应。两头的好处都没了，只剩复杂。
  • 事件驱动 = 分布式单体：服务拆了，但靠事件串成一条强耦合链，谁也不能独立上线。
  • Timeout 反模式（Mark Richards）：超时设短了误杀，设长了错误反馈极慢；正解是熔断器 + 心跳/探活，而不是调参数。
  • 为了架构而架构：CQRS、事件溯源在错误的土壤上一定失败。先问"这个域真的需要重放/审计/擦写分离吗"。

选型草图

需求形状可以选
高吞吐、要回放、多消费者各自读全量Kafka / Redpanda / Pulsar（日志型）
复杂路由、优先级、延迟队列、事务性队列RabbitMQ
轻量、云原生、极简 pub/sub 或请求-回复NATS / JetStream
不想引入新基础设施、量不大Postgres 表 + Outbox + LISTEN/NOTIFY
托管云、按条计费、扇出SNS + SQS / EventBridge / Pub-Sub

先定投递语义（至少一次？保序？回放？），再定产品。反过来的选型都会返工。

照镜子：这个项目自己就是个小 EDA

wombat-go 的 pkg/daemon 几乎踩遍了上面每一条，而且踩得挺标准：

  • inbox 即通道：消息、审批决定、定时器到期、任何 POST /api/events 都落成一行， 请求返回即安全——这是"持久化通道"，不是内存队列。
  • dedup key：同一事件重复投递只收一次 ⇒ 幂等消费者。
  • 事件带头：kind / source / from，与 Wikipedia 说的 header 一致； 模型看到的是"谁说的"，而不是把 webhook 的 payload 当成用户指令。
  • outbox 反向通道：agent 说的话进 outbox，客户端 ?after=&wait= 长轮询并 ack， 也支持 webhook 推送——至少一次 + 客户端 ack。
  • 序号是会话全局的+ Last-Event-ID：把 SSE 断线重连变成了"从漏掉处续读"， 这正是日志型通道给的能力。
  • 租约（lease）与 fencing：一次只有一个 worker 跑某会话，死掉的进程停止续租， 别人接管后把没跑完的补上——分布式下"谁负责"的问题在这里被收敛掉了。

反过来看，这份设计最"事件"的一点是没有任何东西能启动一轮对话，除了 inbox 里的一个事件—— 连 agent 自己的定时器也是往 inbox 丢事件。这就是 EDA 的形状。

我的三个判断

  1. EDA 的收益在边界，成本在中间。 跨团队、跨系统、峰值不均——收益巨大；只是把三个类解耦，纯亏。
  2. 真正的门槛不是消息队列，是"一致性 + 幂等 + 可观测"。 选 Kafka 只要一天，把 outbox、去重、追踪做对要半年。
  3. 先有事件风暴，再有代码。 能不能用过去式给一件事命名、说清它的边界，比选型重要得多。
